**Rev 3 is ready for M0 scaffolding, but I would hold M0 sign-off and resolve the M1a/M1b acceptance criteria before coding.** The three-package split and installed-build matrix are clear. The skeleton implements the action and both messages, but it makes interface choices the plan leaves implicit.

The interface manifest omits `action_msgs` and `service_msgs`, which action generation looks up. CI installs ROS before checking dependencies and searches simulated output for `pip install`, which misses installer choices for already-satisfied keys. Add a per-package manifest table, declare both action dependencies, and check each external key’s rosdep installer and apt candidate in all three matrix legs before installation. Define that M0 covers the skeleton plus named early probes, and rerun the same gate as later dependencies land. - **Resolve action rejection semantics before freeze — `01-architecture` §§5/8, `03-milestones` M3.** A ROS 2 action rejection gives the client an acceptance flag. Result codes belong to accepted goals. As written, clients cannot receive `BUSY` or `INVALID_GOAL` under §5’s rejection policy, and §8 promises a `TF_UNAVAILABLE` result for a refused goal. Keep admission rejection for busy, invalid and latched goals, explicitly mark those cases as having no result payload, and make clock preflight an accepted goal that aborts with `TF_UNAVAILABLE`. Exercise the MoveIt-facing terminal outcomes in the M2 probe before the M3 freeze. Define the relative-rotation pairs, axis-spread statistic, Jacobian parameter scaling and weighting, then say which checks apply before fitting, after outlier removal and inside each fold. Commit those definitions with the M1b sweep so thresholds have stable meaning. [Solver and gates](/home/anson/workspaces/handeye_autopilot/docs/design/02-features.md:172)
